One bad query, one blank page

When I started, errors were printed straight onto the screen for whoever happened to be looking, and nowhere else. Turning that off was right, and for a while it made things worse. A page is built from many queries, and in PHP an uncaught exception ends the whole request. One broken query anywhere, and the user got a blank white page: no message, no clue, and no log yet to say what had happened.

The fix that worked

So the database layer caught every query error, logged it, and returned an empty array. The caller got exactly the shape it expected. A broken panel came up empty while the rest of the page kept working, an endpoint still returned valid JSON the screen could render and report on, and the log said why. Pages stopped dying. It was a good trade, and for a long time it looked like the end of the story.

The caveat

An empty array also means "nothing found". And code doesn't only display what it reads. It acts on it. "No existing record" is a reason to insert one. "Nothing found" is a reason to skip a step. Once empty could also mean "failed", those branches were acting on an answer that wasn't real, and nobody was told. A blank panel is honest about being broken. A skipped write is not.

Then comes the question you don't want to answer: how many places? A scan found 172 where code acted on a read that might have failed. In a sample of twenty, eight would act on wrong data and four would silently skip a write. The crash you can see was never the scary part. The scary part is the record that never got written, behind a screen that said it was saved.

Every failure needs a witness.

How it got worked out

Simply throwing again would have brought the blank pages back. So the throw had to come last, after everything that would catch it, record it and tell someone was already in place. That meant closing six silences, in order, each one a place where something could break and nobody would ever find out.

  1. Writes

    Saves that said they worked

    Older screens reported success whether or not the write happened. Someone clicked Save, saw it confirm, and moved on from a change that was never stored. Every failed write now passes through one guard in the database layer, and the screens check it before they answer.

  2. Background jobs

    Proving a job actually ran

    Cron output went nowhere. A job could die and stay dead until someone noticed the data it fed had gone stale. Each job now records a heartbeat after every phase, and an hourly check emails when one is late. Its first real catch was a broken every-minute job, flagged and fixed within the hour.

  3. Browser

    Errors stop going to the user

    Error details reached only the person who hit them. Now they go to the log, on the web and in cron.

  4. Alerting

    Every error emailed within a minute

    A job reads only what was added to the log since its last pass, groups repeats so one error doesn't become a hundred emails, and keeps its state outside the database, because the day the database is down is the day you need that email most.

  5. Outside view

    Watching from outside, and timing everything

    A one-word health check for an outside uptime monitor, and a log line for any request over 5 seconds. The slow-request log pointed straight at one integration as the next performance target.

  6. Reads

    A failed query is no longer "no rows"

    Finally, in the modern endpoints a failed query throws. One boundary catches it and still answers with a well-formed response, so the page survives, but it now says "Something went wrong (ref 1a2b3c4d)" instead of "nothing found". That ref leads straight to the failing SQL in the log, and SQL never reaches the user. The page stays alive, and it no longer lies.

The alert's first real catch

A cleanup removed a method a search said nobody called. Every check said the deletion was safe. An old report did call it, with different capitals, and PHP method names are case-insensitive. The next time someone opened that report:

+0 sfatal error: call to undefined method
+3 salert email sent
+6 minfix committed

Before the alert, that user would have seen a white page until they gave up and told someone.

What I'd tell anyone doing this

An empty result is a claim, not a fact

If "failed" and "nothing found" look the same, every caller is guessing which one it got.

The alerter must not depend on what it watches

If the database is down, that is exactly the email you need.

Measure before you make failures loud, and prove each guard by breaking it

Count what a stricter rule would surface before switching it on. A guard that has never fired hasn't been tested.
