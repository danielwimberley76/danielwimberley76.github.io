Case study · AI coding agents · Live production

Five AI agents. One live codebase. No quiet minutes.

I'm the Principal Software Architect on a company's operations platform. It is in use every minute of the working day, by people in the office and people out in the field, and a minute of downtime gets felt somewhere. And most days, four or five Claude Code sessions are changing it at once. The agents are the rest of the team.

That sounds productive until you've lived it. Two sessions edit the same file and one quietly wins. A commit sweeps up a change nobody will claim. A session says "done" and leaves errors in the log that no one will ever read, because every other session assumes they belong to someone else. Every one of those mistakes lands on a system people are using right now. This is how I keep the agents from hurting it, or each other: every rule that matters is enforced by a hook, not written in a prompt.

Prompts are advice. Hooks are law.

A session once committed to the shared history with a message that was a single character: an at sign. No description, no task number, nothing a person could ever trace. I wrote a rule into the agents' memory so it would never happen again. Weeks later, another commit with a message of just an at sign. The agent had read the rule. It had simply weighed it against everything else in its context, and the rule lost. That was the day a written rule stopped feeling like protection.

So every rule that protects production or another session's work became a Claude Code hook: a small script the harness runs at a fixed point in the agent's loop, which can refuse the action outright. The agent can't talk its way past it, and neither can I by accident.

Five incidents, five hooks

Every one of these happened, and every one looked fine right up until it didn't. Each is now refused by a hook.

Git

The amend that rewrote someone else's commit

What happenedA session noticed a typo in its commit message and amended. Routine. What it couldn't see: in the seconds between its commit and its amend, another session had committed. The amend didn't fix a message. It erased someone else's work, and nothing told either of them.

The hookAfter every commit, a hook records the commit this session just made. Before an amend, it checks that the current commit is still that one. If anyone has committed since, the amend is refused.

Git → production

The sweep that reached production

What happenedgit add . is the most natural command in the world. This one picked up another session's half-finished file, which shipped to production ahead of the database change it needed, and a screen people were using broke. The fix was quick. The hard part was the stretch before it: whose file is this, how did it get out, and what else went with it? Both sessions involved had read a doc warning against exactly this.

The hookBroad adds, commit -a and bare stashes are refused. A session names the paths it wrote, and an edit ledger tells it which uncommitted files are its own.

Extending this hook nearly opened a new hole: recording HEAD on git add would have let a session claim another's commit as its own and wave through their amend. It was caught in review before it shipped.

Production data

The filter that read correctly in English

What happenedYou know the feeling: a write you trusted touched far more than you meant, and you don't yet know how far. Our orders table has a status column that sounds like "delivered or not" but is really an alive flag: it never holds "delivered". When code moved, a date bound was dropped, and a scheduled job used that column alone to pick its rows, so it rewrote a field on historical records it should never have touched. Then the repair script used the same filter, so the fix carried the same blast radius as the bug. Measured afterwards, it matched about 700 times the rows it was meant to.

The hookAny script that writes to production in bulk must run through a guard that counts the rows its filter matches, refuses if the count exceeds the declared ceiling, writes a rollback file, and runs in a transaction. A hook refuses to run a production write script that doesn't use it.

No SQL review reliably catches that filter, because it reads correctly. A row count before the write catches it in one second.

Hooks themselves

The guard that was off for every session

What happenedA guard with a syntax error isn't a broken guard. It's no guard at all, and nothing tells you. I edited the production-write hook in several small steps, and between two of them it briefly didn't parse. A crashed pre-command hook doesn't block, so for that moment every running session was unguarded and none of them knew. Earlier, its first version couldn't read Git Bash paths and allowed everything. Once fixed, it grepped the raw command and refused four ordinary commits in one afternoon. Each was forced through with the override.

The ruleHooks are production code. Build and test in a scratchpad, replace in one write. Parse the command instead of grepping it. Break every new check on purpose before trusting it.

Breaking checks on purpose earns its keep: a dependency-ordering check, deliberately broken, kept 14 of 15 tests green, because alphabetical order happened to match the right order.

Deploys

Deploys keyed to my literal words

What happenedThe most dangerous command an agent can run is the right one, a little early. Permission rules couldn't express "only when I say so". An "ask" rule didn't prompt in auto mode, and a "deny" rule blocked real deploys too, so I ended up pasting deploy commands myself.

The hookPush and deploy unlock for one hour only after my whole message in that session is "deploy" (or "deploy #N"). The word inside a sentence doesn't count, and neither does a message relayed from another session.

About 28 refusals across 8 sessions, including a message that only mentioned "deploy" mid-sentence and a script that merely wrote the deploy command out as text.

What I'd tell anyone doing this

Choose fail-open or fail-closed on purpose, per check

The production-write guard and the deploy gate fail closed. Lint on commit fails open when its tools are missing, and only judges the files being committed, never another session's work in progress. A gate a session has to fight teaches it to reach for the override.

Give each session a ledger of its own writes

With five sessions in one tree, "what's uncommitted" is everyone's mess. A post-edit hook records which session wrote which file, so each session commits only its own work, and the stop hook holds it to that.

One folder, one address, per task

Five sessions editing one folder break each other mid-edit: code that ran a second ago now fails, because another session is halfway through a file you never touched. More than two sessions in the main folder is now against the rules: every other task gets its own git worktree and its own local web address, like task-123.wt.localhost, served by a wildcard virtual host. One round of browser testing ran against the wrong code because a worktree's address was quietly answered by the main folder. Now each new worktree has to prove its address serves its own files before anyone uses it.

Put a byte budget on what agents load

About 185 short docs record the system's traps. The part every session loads is held under 75 KB by a check in CI. It had crept to 101 KB before the check existed. Rules over budget move into the doc they belong to.

Give the agent narrow keys, not your keys

Agents never use my keys. They get one key that can run a fixed set of read-only commands on the server. That key is how sessions confirm a deploy landed, without being able to change anything.

Mine your transcripts for friction

A permission prompt you've clicked through a hundred times stops being a check. You approve the next one without reading it. I audited every prompt I had clicked through, and hundreds were for edits that were already allowed. A narrow permission hook now answers those, so the prompts that remain mean something. One routine went from 37 prompts over 43 minutes to 3 in about 7.
